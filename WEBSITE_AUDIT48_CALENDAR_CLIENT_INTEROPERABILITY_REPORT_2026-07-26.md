Date: 2026-07-26  
Scope: Google Calendar, Apple Calendar, and Outlook compatibility for Polymythcal ICS downloads and subscriptions  
Status: all locally executable work passes  
Boundary: no security audit was performed

## Result

- 9 of 9 permanent interoperability tests pass.
- 857 of 857 ICS files pass strict UTF-8, CRLF, envelope, folding, identity, time, and semantic checks.
- 4,172 of 4,172 VEVENT representations parse successfully with the independent `icalendar 7.2.0` RFC 5545 implementation and survive serialize-and-reparse validation.
- 833 canonical event files remain aligned with the 833 canonical data records.
- 12 explicit legacy ICS URLs remain byte-identical to their canonical targets.
- 12 focused or historical feed files remain aligned with the feed manifest and canonical stable UIDs.
- The largest physical content line is now exactly 75 octets.
- Local HTTP responses return `text/calendar; charset=utf-8` and the exact generated bytes for canonical, legacy, and subscription files.

## Defects found and fixed

### Feed continuation lines exceeded the RFC 5545 folding budget

The prior Audit 47 archive contained 1,416 continuation lines of 76 octets across ten focused feed files. The folding function allocated 75 octets to continuation content and then prepended the mandatory continuation SPACE, producing a 76-octet physical line. RFC 5545 section 3.1 sets a 75-octet line limit and counts the continuation whitespace as part of the physical line.

The feed builder now allocates 75 octets to the first physical line and 74 content octets to each continuation line. UTF-8 code points remain intact at every fold boundary. The current corpus contains zero lines above 75 octets.

### The historical deadlines feed lost CRLF transport framing

`deadlines.ics` was created by reading `opportunities.ics` in universal-newline text mode. The prior archive therefore contained 1,943 LF line endings and zero CRLF line endings in `deadlines.ics`; a strict CRLF parser saw its 84,959 bytes as one physical line. It also ceased to be byte-identical to the historical target it aliases.

The builder now decodes the generated bytes without newline conversion. `deadlines.ics` is byte-identical to `opportunities.ics`, uses CRLF throughout, and parses into the same 125 VEVENT components.

### A bare carriage return could survive organizer text escaping

The per-event builder normalized CRLF and LF but lacked a final bare-CR conversion. Future organizer text containing an isolated carriage return could have introduced a control character into a content line.

The text escaper now converts CRLF, LF, and bare CR to the RFC 5545 escaped newline form. A permanent edge-case fixture covers bare CR, LF, commas, semicolons, backslashes, long accented text, and Chinese characters.

### Calendar media delivery depended on extension inference

The local server already mapped `.ics` to `text/calendar`, while the deploy header contract lacked explicit rules for the canonical, legacy, and focused-feed URL trees. This mattered alongside the existing `X-Content-Type-Options: nosniff` response policy.

`_headers` now explicitly returns `Content-Type: text/calendar; charset=utf-8` for both `/polymythseminars/ics/*.ics` and `/polymythseminars/feeds/*.ics`. Canonical event pages, localized event pages, static subscription pages, and dynamically rendered feed links now declare `type="text/calendar"`.

### Calendar compatibility lacked an independent acceptance gate

Previous checks established file presence and legacy byte equality. They did not independently parse every file or validate client-facing transport invariants.

Audit 48 adds a pinned independent parser and a permanent nine-test gate covering:

- exact canonical, legacy, and feed inventories;
- UTF-8 without a BOM;
- CRLF-only framing and final CRLF;
- maximum 75-octet physical lines;
- required VCALENDAR and VEVENT properties;
- parser acceptance and serialize-and-reparse acceptance;
- stable UID behavior across event files and feeds;
- canonical HTTPS URL behavior for every legacy file;
- exact-time UTC conversion and DST boundaries;
- all-day exclusive DTEND behavior;
- DTSTART and DTEND value-type agreement;
- positive event duration;
- source title, status, start, end, and identity parity;
- absence of invitation semantics such as ATTENDEE and ORGANIZER;
- focused-feed predicate and manifest parity;
- English and French calendar-link media declarations;
- local HTTP status, media type, charset, and byte delivery;
- pathological Unicode, punctuation, newline, DST, multiday, and legacy-ID fixtures.

## Client-specific coverage

### Google Calendar

Google documents desktop import for ICS files and identifies the VCALENDAR header/footer, VERSION, PRODID, and VEVENT boundaries as the required iCalendar envelope. Every current and legacy file satisfies that envelope. The gate also checks the stronger RFC 5545 requirements, exact data semantics, and independent parser acceptance.

### Apple Calendar

Apple documents `.ics` as its event import format on macOS. Every Polymythcal file now has strict RFC 5545 transport framing, deterministic Unicode folding, UTC exact times, DATE-valued all-day intervals, stable UIDs, and explicit calendar media delivery.

### Outlook

Microsoft documents both `.ics` import and web subscription. The focused feeds expose stable HTTPS URLs, stable event UIDs, `METHOD:PUBLISH`, calendar names, explicit `text/calendar` delivery, and complete RFC 5545 framing. The historical deadlines URL remains a byte-identical alias of the opportunities feed.
